# 原理与验证边界

## 原始案例

2026-10-26，Windows 上的一位用户启用了代理客户端的系统代理，但 ChatGPT 桌面版反复显示 `reconnecting…waiting for work`。本地日志中出现 WebSocket 建立前关闭及 Work rendezvous 超时；代理规则已经覆盖 ChatGPT，因此继续添加域名规则无法说明根因。

不携带凭证的对照请求在直连时超时，显式走本地代理时能收到 HTTP 响应。给应用显式传入代理环境变量和 Chromium 代理参数，完全退出后通过该入口重新打开，用户多次测试并确认重连提示消失。原始安装包版本为 `26.1021.3705.0`（包名称 `OpenAI.Codex`），本地代理为 HTTP/混合监听，TUN 关闭。

这里只记录通用结论；项目不包含原始日志、个人节点、订阅、账号信息或原始完整代理 YAML。

## 为什么显式代理启动可能有效

桌面应用可能包含 Chromium、Node 与本地执行器等不同网络组件。Windows 系统代理不必然被每个组件以同样方式读取。本工具给新进程提供明确的代理环境，同时给 Chromium 提供代理启动参数。子进程可以继承这些变量；真正是否使用仍由组件实现决定。

使用 `ProcessStartInfo.EnvironmentVariables` 为新进程建立环境，不写入当前用户或系统环境。`NO_PROXY` 被设为本地回环地址，使应用的本地服务连接可绕过代理。代理 URL 只允许本机 HTTP 监听；本工具不实现代理协议、不供应节点、不修复远端服务。

## 已验证和待验证

- 原始简单启动入口已得到用户恢复连接的反馈。
- 通用项目增加了自动检测、安装、检查和卸载；这些行为有自动化测试。
- 自动检测只是 TCP 端口检测，不能保证端口确为 HTTP 代理，也不能保证代理链路或特定地区可用。
- 匿名诊断获得 401/403 不能证明已登录 WebSocket 握手成功，也不能排除代理或中间设备响应。
- 不是所有应用版本或网络组件都会采用这些环境变量与启动参数；不承诺永久解决所有重连问题。
